01Dimensão jurídica · cadeia HMAC tamper-evident

Toda alteração em entidade auditável entra numa cadeia hash criptográfica encadeada. Mexer no banco quebra a cadeia. Reconciliação cross-process bit-a-bit garante que Java (Spring Boot) e Node (gateway + chat-ia) compartilham a mesma cadeia por organização. Prova matemática reconstruível — vale em juízo, vale em TCU, vale em CGU.

ElementoImplementação
Versão da cadeiaVersão 3 · sincronizada bit-a-bit entre serviço Java (Spring Boot) e serviço Node (gateway + chat IA)
AlgoritmoHMAC-SHA256 · entrada encadeada: hash anterior + tipo da entidade + ID + ação + usuário + data ISO + delta + organização
Lock por organizaçãoBloqueio transacional dedicado por organização · previne escritas concorrentes que poderiam bifurcar a cadeia · idêntico em Java e Node
Captura universalListener Hibernate intercepta toda inserção, atualização e remoção de qualquer entidade auditável · sem decorator manual em cada classe
Falha em produçãoSem chave secreta configurada em produção, o sistema não sobe — fail-fast intencional · em desenvolvimento usa fallback explícito
Métricas de auditoriaContadores de sucesso e falha (com tag de causa) e tempo de escrita com percentis (mediana, p95, p99) expostos em formato Prometheus
Pacote compartilhadoBiblioteca interna usada por Java + Node + Chat IA · garante consistência cross-service da cadeia

Por que isso importa pra Lei 14.133

A nova lei amplia responsabilização pessoal do fiscal e do gestor. Quando algo dá errado, a pergunta do controle interno e do TCU é: "como você comprova que o registro não foi alterado depois?" Em sistemas tradicionais, a resposta é "o log mostra...". Em sistemas com HMAC chain, a resposta é "qualquer auditor pode recomputar a cadeia e verificar — se um único byte foi alterado, a cadeia toda inválida". Diferença prática gigante em juízo.

02Dimensão técnica · multi-tenant fail-closed

Princípio fail-closed: requisição sem organização identificada é bloqueada. Cada organização vê apenas seus dados, sempre. Não é "feature de segurança ativável" — é regra arquitetural desde o primeiro commit. Vazamento cross-org é impossível por construção.

requireDataScope middleware (Express)

Caching multi-camada: orgIdCache + userIdCache (500 entries · 30min TTL · LRU eviction). resolveOrganizationDbId via SELECT id FROM organization WHERE external_id. Permission scope parser (all/team/own). admin.full override.

gov.br · Login Único do Cidadão · provider OIDC pré-mapeado

O gov.br segue o padrão OAuth 2.0 + OpenID Connect Core 1.0 com PKCE obrigatório — protocolo já entendido nativamente pelo NuPIdentify. Por isso, a integração é configuração, não código: existe manifesto pronto com endpoints corretos de staging e produção, mapeamento de claims (CPF, email, nível de confiabilidade Bronze/Prata/Ouro), e regras de step-up que exigem nível Ouro para ações de maior impacto (ex: fechamento de contrato acima de R$ 100k).

Pré-requisito legal para ativação em produção

A liberação da credencial de produção do gov.br depende de: (a) aplicação hospedada em domínio oficial (.gov.br, .mil.br, .jus.br, .tc.br, .leg.br, .def.br, .mp.br, .edu.br) conforme Portaria SGD/MGI nº 7.076/2024; (b) credenciamento via integracaoid@gestao.gov.br feito por servidor com conta gov.br nível Prata ou Ouro do órgão; (c) aprovação prévia em ambiente de homologação. Implicação prática: cada órgão contratante credencia sua própria instância EasyNuP (hospedada no domínio do órgão). O ambiente staging do gov.br já fica disponível para demonstração imediata assim que o cliente solicita.

05Dimensão técnica · webhook framework com HMAC + IP whitelist

Toda integração com sistema externo passa por framework comum. POST /api/webhooks/inbound/:slug com HMAC-SHA256 verification, IP whitelist CIDR matcher, idempotency dedup, replay protection. 4 webhooks atualmente mapeados.

Verificação HMAC timing-safe

Header X-Webhook-Signature · formato sha256=<hex> · validação via crypto.timingSafeEqual (não vulnerável a timing attack). Adapter Sentinel valida X-Sentinel-Signature com mesmo padrão.

IP whitelist + idempotency + replay protection

CIDR matcher (isIpAllowed function) · webhook_execution_log dedup pra requisições repetidas · validação de timestamp pra impedir replay tardio.

4 webhooks mapeados

Tolgee (atualizações de i18n) · NuPIdentify (eventos de auth: login.brute_force_blocked, permission_denied) · Sentinel (findings inbound) · generic (custom workflows).

Cross-repo security event broadcast

Identify ↔ EasyNuP via HMAC headers · SecurityEvent table propaga eventos com action (64 chars) · provider · slug · source_ip · user_agent · organization_id · user_id · detail · request_id · created_at.

07Dimensão operacional · observabilidade nativa

Métricas Prometheus em pontos críticos · request tracing cross-process via Sentinel Probe · logs estruturados com requestId/sessionId propagados. Quando algo quebra, equipe sabe em segundos onde foi — não é "preto e branco", é raio-x.

Métricas Prometheus custom

08Multi-tenancy de mensagens · HybridMessageSource

Cada organização pode sobrescrever mensagens do sistema (erros, notificações, e-mails) sem afetar outras. Cascata 3 níveis: override da org → override global → fallback Tolgee/ResourceBundle. Cache Caffeine (60s TTL · 10k entries max) com hot-reload sem Redis.

Sensitive labels com approval workflow (ADR-036)

Mensagens marcadas como sensitive:financial · sensitive:legal · sensitive:auth exigem aprovação humana antes de virar publicadas. Webhook do Tolgee dispara notificação para aprovador (permissão i18n.sensitive_messages.approve). Two-eyes obrigatório para mudança em texto que pode virar prejuízo ou interpretação errada.
